# Memory subsystem audit — 2026-05-12

**HEAD:** `a5999e2`
**Scope:** Memory pipeline end-to-end — extraction, store, search, forget, stats, replay integration, vec0 linkage
**Calibration bug (today's reference):** `facts.source_turn_id` FK / writer hash mismatch (fixed in `a5999e2` by dropping the FK)
**Live probe context:** PID 18811 has been up ~1h45m; `~/Library/Application Support/Jarvis/jarvis.db` has 8 turns, 1 fact, **0 facts_vec rows**, 1 facts_fts row. Today's session_id `8FC15E7A-F2B4-4FCA-A79F-947E34C5F27B`.

Audit ran read-only against the live DB plus the package source. Three CRITICAL findings, two HIGH, one MEDIUM, two LOW. No findings re-flag pre-2026-05-04 issues already closed.

## Findings (severity-ordered)

### M-1 (CRITICAL): `facts_vec` is never written — semantic search branch is permanently empty

**Path:** `packages/Memory/Sources/Memory/MemoryStore.swift:132-246` (`applyOp` / `insertNewFact`)
**Symptom:** `search_memory` works in keyword mode only. The hybrid SQL's `vc` CTE (line 43-48 of `MemoryQueries.hybridSearchSQL`) returns zero rows on every call. RRF degenerates to FTS5-only ranking. Semantic recall ("dog" → "Toby" via embedding similarity) silently doesn't work.
**Root cause:** `applyOp` inserts into `facts` (via the `INSERT INTO facts(...)` block at line 168-182) and the schema's FTS5 trigger mirrors `facts_fts` automatically — **but nothing inserts into `facts_vec`**. There is no embedder call in `insertNewFact`, no INSERT INTO facts_vec anywhere in `MemoryStore.swift`, no equivalent path in `MemoryExtractionOrchestrator.process`, no path in `MemoryExtractor.extract`. The schema exists, the extension is loaded (`vec_version: v0.1.6`), the embedder client (`OllamaEmbeddingClient`) exists and works — but no producer wires them to the writer side.
**Evidence:** Live DB — `SELECT COUNT(*) FROM facts_vec_rowids` → `0` despite 1 fact present. `SELECT COUNT(*) FROM facts` → `1`. The Toby fact (`id=1`, subject="user", predicate="name is", object="Toby") has an FTS row but no vec row. Schema-vs-writer impedance mismatch identical in shape to today's FK calibration bug — the schema declares a column/table the writer never produces.
**Recommended fix:** Inside `insertNewFact`, after the `INSERT INTO facts` succeeds and `newId` is known, run the query embedder against `"\(subject) \(predicate) \(object)"` (or a richer text projection) and `INSERT INTO facts_vec(fact_id, embedding) VALUES (?, ?)` inside the same transaction. The embedder is async — `MemoryStore` is an actor so awaiting is fine, but the embedder must be injected (the current `applyOp` has no embedder reference; `installMemory` builds the embedder for `HybridSearch` only). Pattern options: (a) make `MemoryStore.init` take `embedder: any EmbeddingProviding?` and skip the vec INSERT when nil; (b) move the embed+insert step into `MemoryExtractionOrchestrator.process` after `applyOp` returns the new `Fact`. Either pins the same actor-owned connection and keeps single-emit invariants intact. Failure mode discipline: log + leave the FTS row (degraded but searchable) rather than rolling back the fact row.

### M-2 (CRITICAL): Replay log poisoned — synthetic `memory-trigger-<hash>` turn_ids break ALL replay flushes since 18:48

**Path:** `App/AppDelegate.swift:2783-2797` (`AppDelegateMemoryReplaySink.record(_:forTriggerTurnId:)`), with downstream FK enforcement in `packages/Replay/Sources/Replay/Schema.swift:15` (`PRAGMA foreign_keys=ON`) and `packages/Replay/Sources/Replay/ReplayLog.swift:195-260` (`flushPending`'s batch transaction).
**Symptom:** Every replay batch since `2026-05-12T18:48:47.211Z` has failed with `SQLITE_CONSTRAINT_FOREIGNKEY` (code 19). The ReplayLog re-buffers the poisoned batch at the front of `pending` (line 239), retries, fails again, and at 3 consecutive failures escalates to `CRITICAL`. Current state per `replay.2026-05-12.log`: ~50+ chronic-failure entries, `batch_size=31` and growing, `consecutive_failures=23+`. The 1 real fact (which fired memoryMutation) is silently lost; so are dozens of real turn-event rows queued behind it (text_delta, tool_call_requested, turn_end). `events.row_id` MAX in replay.sqlite is from before the poisoning — observability is dead until the process restarts.
**Root cause:** When `MemoryStore.recordMemoryMutation` (line 248-272) fires, it routes through the sink with a synthetic TurnID `"memory-trigger-7747877241524896942"` (the FNV hash from `MemoryExtractionOrchestrator.stableHash`, formatted as a string). `replay.sqlite`'s `events.turn_id REFERENCES turns(turn_id)` is a real FK with `foreign_keys=ON`; there is no row in `turns` with that synthetic id, so the INSERT inside the batch transaction throws `SQLITE_CONSTRAINT_FOREIGNKEY`. Because `flushPending` wraps the WHOLE batch in one transaction, the poisoned event takes every real event in the same batch down with it on rollback. The re-buffer logic doesn't filter — same poison gets retried forever. Identical FK-vs-writer impedance shape as the calibration bug, in a second DB.
**Evidence:** `~/Library/Logs/Jarvis/replay.2026-05-12.log` first 50 lines all show `turn_ids=...,memory-trigger-7747877241524896942`. Real session turn_ids (`5F3E38F7-259F-4060-8C17-EB304A042826`, `A4A95D0F-64F9-49D9-88A4-1ECF53B9367A`) are stuck in the same batch and never persist. `sqlite3 replay.sqlite "SELECT kind, COUNT(*) FROM events GROUP BY kind"` shows only events from before 18:48 — no `memory_mutation` rows ever, despite the 1 fact written today.
**Recommended fix:** Two layers, pick at least one:
1. **Don't synthesize a fake turn_id.** Either thread the real triggering `TurnID` (UUID) through to the sink (requires plumbing the real ID through `MemoryExtractionCoordinator` → `Orchestrator.process` → `applyOp` → `recordMemoryMutation`; the orchestrator already has `job.turnId` — pass it through alongside the Int64 hash and use the real one when emitting to replay), or accept that memory mutations aren't pinned to a single turn and add a sentinel `turns` row up-front for them (`session_id = current`, `turn_id = "memory-system"` or per-session). The latter is one extra INSERT at session start.
2. **Defensive batch-splitting in `ReplayLog.flushPending`.** When a batch fails, retry events individually so one poisoned row can't take 30 others with it. This bounds the blast radius even if a new poisoned-id pathway sneaks in later.

### M-3 (CRITICAL): Agent has no preamble cue to call `search_memory` — proactive recall is dead by discovery gap

**Path:** `packages/AgentCore/Sources/AgentCore/ContextBuilder.swift:64-74` (`selfAwarePreamble`), plus the absent memory-hydration wiring in `App/AppDelegate.swift:1685` (`systemPrompt: ContextBuilder.systemPrompt(for: .empty)`).
**Symptom:** Today's session perfectly reproduces this. Turn 1: user says "what is my dog's name?". The agent has `search_memory` registered in the tools array (verified: 10 tools probed `ok`), but answers "I don't have anything in memory about your dog. What's their name?" without calling it. Turn 2: user says "Toby". Agent: "Got it — Toby. I'll remember that." It does NOT call `search_memory` first to check, never has, and live logs show zero `searchFacts:` log lines anywhere in `~/Library/Logs/Jarvis/`. (`memory.search` channel is silent across all sessions.)
**Root cause:** The preamble enumerates 7 introspection tools by name — `list_audio_devices, get_active_audio_route, get_self_state, list_camera_devices, get_time, get_clipboard, run_applescript` — but **omits both `search_memory` and `forget_fact`**. Anthropic's tools array is canonical, but the model's preference is shaped by the preamble's explicit "always prefer calling those tools over giving generic instructions" rule. Without a name in the preamble, `search_memory` falls into the bin of "tools the agent technically has access to but won't think to use." Confirmed by behavior. The `TurnContext.memoryHydration` field exists in `ContextBuilder` (line 41) and `systemPrompt(for:)` will splice it in if non-nil, but **the only production call site at `AppDelegate.swift:1685` passes `.empty`** — there's no glue that pre-populates `memoryHydration` from a `HybridSearch` pass before each turn. So neither path (proactive tool call nor auto-hydration) is alive.
**Evidence:** `grep -rn "search_memory" packages/AgentCore/` → only the audit comment, never in the preamble. `grep -rn "memoryHydration" App/` → only the type declaration; no wiring. Live `system.2026-05-12.log` lines `BootHealth: subsystem=mcp ... search_memory` present. Live `memory.*log` files have zero `[memory.search]` channel emissions. Replay events table shows 19 `tool_call_requested` rows — all `get_time` / `get_self_state` / etc., zero `search_memory`.
**Recommended fix:** Add `search_memory` (and arguably `forget_fact`) to the preamble's named-tool list, with a specific cue: e.g., `"When the user references something they may have told you before, or asks 'do you remember…', call search_memory FIRST. Never claim to remember without searching."` The `SearchMemoryTool.toolDescription` already contains that sentence — it's just not in the preamble, where the cache-locked early-prompt nudge actually lives. Optionally wire `TurnContext.memoryHydration` in `AppDelegate.swift:1685` to call `HybridSearch.searchFacts(query: input.userText, k: 5, ...)` before each turn, but this needs orchestrator API plumbing — the named-tool fix is much cheaper and ships M-3 alone.

### M-4 (HIGH): `MemoryExtractionOrchestrator.process` still hashes `TurnID` and stores the hash in `facts.source_turn_id` — correlation is permanently broken

**Path:** `packages/Memory/Sources/Memory/MemoryExtractionOrchestrator.swift:122-152` (`process` body + `stableHash`)
**Symptom:** After today's FK fix, fact INSERTs succeed, but `facts.source_turn_id` holds the FNV-1a hash of `TurnID.rawValue` (a UUID string), not a real `turns.id` rowid. Querying "what turn produced this fact?" can't be answered — `SELECT t.* FROM facts f JOIN turns t ON t.id = f.source_turn_id` returns nothing. The replay-trigger TurnID surfaced via the synthetic `memory-trigger-<hash>` string (see M-2) inherits the same hash. The schema's stale-comment-now-truth: "the writer's correlation tag and `turns.id` are disjoint number systems by design."
**Root cause:** When the FK was dropped in `a5999e2`, the writer-side change to use a real `turns.id` rowid wasn't made — the FNV hash is a Phase-7 artifact that survived the fix. The orchestrator has `job.turnId: TurnID` (UUID string) and the turns table autoincrement `id INTEGER PRIMARY KEY` — but no lookup translates one to the other. The `B-02` patch (commit `48ad8d6`, `AppDelegate.swift:1753-1766`) writes turn rows BEFORE memory extraction enqueues, but doesn't return the rowid; even if it did, there's no plumbing to feed it back into the orchestrator.
**Evidence:** Live DB `SELECT source_turn_id FROM facts;` → `7747877241524896942` (an FNV hash, easily verified by hashing today's TurnID). No row in `turns` has `id=7747877241524896942`. The schema comment at `MemorySchema.swift:35-50` openly acknowledges this — but acknowledgement isn't a fix. Anyone trying to debug "which turn caused this fact?" via SQL will get blank rows forever.
**Recommended fix:** Two surgical options:
1. Drop `source_turn_id` from the schema entirely if no consumer reads it (and document that fact-to-turn correlation is via `valid_from` timestamp proximity instead). Cleaner.
2. Make `B-02`'s `appendTurn` return the new rowid, thread it through the `flushPair` callback (return a triple `(userText, assistantText, userTurnRowId)`), and have `MemoryExtractionCoordinator.start`'s `turnContent` closure return it; pass it as `sourceTurnId` through to `applyOp` instead of the FNV hash. Drop `stableHash` entirely.

Option 1 is a one-day fix; option 2 is half a day and preserves the correlation. The current state — silently storing nonsense — is the worst of both worlds.

### M-5 (HIGH): `MemoryQueries.hybridSearchSQL` passes raw user text directly to `facts_fts MATCH ?` — punctuation crashes the query

**Path:** `packages/Memory/Sources/Memory/MemoryQueries.swift:33-63` + `packages/Memory/Sources/Memory/HybridSearch.swift:32-57`
**Symptom:** Real user queries like `"what is my dog's name?"`, `"remember when I said X?"`, or anything with an unescaped `?`, `:`, `-`, `"`, `*`, or FTS5-reserved operator throws `fts5: syntax error near "..."` at the SQLite layer, propagates as a thrown `MemoryError`, and the agent gets a tool-call error from `search_memory` instead of results. The replay shows zero `search_memory` calls today, so we have no live evidence yet — but the moment the agent does start calling it (per M-3 fix), every natural-language query with punctuation will fail.
**Root cause:** `HybridSearch.searchFacts` (line 32-57) passes `query` straight through to `MemoryStore.runHybridSearchSQL` (line 311-339) which binds it to `MATCH ?` positional parameter. FTS5's MATCH syntax accepts a small grammar (terms, AND/OR/NOT/NEAR, column filters, phrase quoting with `"`); raw natural language with `?` or `'` characters is a syntax error.
**Evidence:** Live DB probe: `sqlite3 jarvis.db "SELECT rowid FROM facts_fts WHERE facts_fts MATCH 'what is my dog name?' LIMIT 10"` → `Error: stepping, fts5: syntax error near "?"`. Same query without `?` works. No sanitization or escaping anywhere in `packages/Memory/Sources/` or `packages/MCP/Sources/MCP/InProcess/SearchMemoryTool.swift`.
**Recommended fix:** Add an FTS5-safe query rewriter in `HybridSearch.searchFacts` before calling the store. Two-line approach for now: strip punctuation, split on whitespace, double-quote each term, join with spaces — turns `"what is my dog's name?"` into `"what" "is" "my" "dog's" "name"`. This is a phrase-OR query and is FTS5-safe. Long-term: an actual query AST. Until done, search_memory is a footgun the agent will inevitably step on.

### M-6 (MEDIUM): `MemoryBootHealthProbe` evidence is misleading after today's FK fix — `0/0 facts` is no longer a hidden-failure signal

**Path:** `App/Boot/BootHealthProbes.swift:32-55` (probe), `App/Boot/BootHealthProbes.swift:179-181` (stale comment about "the Toby case")
**Symptom:** The probe still reports `state=ok evidence="N turns, 0/0 facts, vec=v0.1.6"` when memory has been written successfully (it just reports row counts at probe time). The 2026-05-12 user-burning bug was caught because the probe was happy with `0/0` while every insert failed; after the FK fix, `0/0 facts` is genuinely a legit empty state. The probe doesn't know the difference between "extractor never fired" and "extractor fired and got NOOP" and "extractor fired and FK-failed."
**Root cause:** Probe asserts schema queryability + vec0 loadability + DB openness — three real things — but doesn't probe the writer end-to-end. After M-1 (no facts_vec writes) is fixed, a stronger probe would also assert `facts_vec` row count tracks `facts` row count within ±1. After M-2 is fixed, the probe could check `replay.sqlite` events table has recent rows.
**Evidence:** Live probe output line `subsystem=memory state=ok evidence="0 turns, 0/0 facts, vec=v0.1.6, sqlite=3.51.0"` from 18:47:35. By 19:00 the user had submitted turns, but the probe ran once at boot — its evidence is stale by construction.
**Recommended fix:** Two complementary improvements:
1. Update the stale comment at `BootHealthProbes.swift:179-181` ("missing models = the Toby case. Embedding step fails, no row inserted in `facts`") — this is no longer accurate. After today's fix the embedding step (which doesn't exist in the writer per M-1) has nothing to do with whether `facts` gets a row. Rewrite as: "missing models = embedder fails → search degrades to FTS-only; extractor fails → no facts inserted at all."
2. Add a parity check to `MemoryStats`: `factsTotal == factsVecCount ± tolerance`, surface as the probe's degraded path. This is the structural defense against M-1-style impedance bugs.

### M-8 (LOW): `MemoryReplaySink.record` is a fire-and-forget detached Task — failures are unobservable from MemoryStore

**Path:** `App/AppDelegate.swift:2786-2797`
**Symptom:** `recordMemoryMutation` calls `sink.record(...)` synchronously per protocol, and the sink dispatches into a detached `Task` (line 2793-2795). Any throw inside the task body (including the FK violation from M-2) is swallowed silently from MemoryStore's perspective. MemoryStore logs success of `applyOp` while the replay event vanishes downstream. Removing this swallow makes M-2 visible at the right layer.
**Recommended fix:** The actor surface is sync, so a true terminal log is hard. But the Task can `do { await replayLog.record(...) } catch { logger.error("replay sink record failed: \(error)") }`. `record(_:for:)` on `ReplayLog` is currently non-throwing — events go into a pending buffer and the throw is at flush time. So this is also a structural observability gap on ReplayLog itself: writes happily succeed at the call site even when flush has been failing for 30 batches. The MemoryStore comment should at minimum acknowledge "best-effort with no terminal observability — failures appear only in replay.<date>.log."

## Verified healthy

- **vec0 linkage on cold start.** `core_vec_init()` runs in MemoryStore's `_vecAutoExtensionRegistered` static-let; `SELECT vec_version()` returns `v0.1.6` on every install. Logged at INFO from `memory` channel in `memory.2026-05-12.log` for all three of today's boots.
- **MemoryStore.appendTurn → recentTurnsForSession (B-02 patch).** Live DB has 8 turn rows for today's session, all four user/assistant pairs intact, role/source/content columns populated, FTS5 trigger fired (1 row in `turns_fts_data`). `sessionHistoryLookup` in `AppDelegate.swift:1647-1669` reads the right session_id (matches `replay.sessions.session_id`). Multi-turn context threading is alive.
- **`MemoryExtractionCoordinator.start` single-consumer invariant.** Coordinator's `subscription = Task.detached` guarded by `guard subscription == nil` — calling twice is a no-op. Drain task filters to `stop == .endTurn` only.
- **`MemoryStore.forgetFact` idempotency.** `WHERE valid_to IS NULL AND forgotten_at IS NULL` makes second call a 0-row UPDATE; returns false the second time. Schema-clean.
- **`MemoryStore.applyOp` supersede transaction.** `beginTransaction` / `commit` / explicit `rollback` on error; the supersede UPDATE asserts exactly 1 affected row. Pattern is correct.
- **`OllamaEmbeddingClient` loopback enforcement + dimension check.** Tested behavior, not just declarative. 768-dim mismatch throws early.
- **`installMemory` boot policy.** Hard-block on init failure (line 1374-1380) — no more silent dormancy from the D-1 era. Probe registers `DormantSubsystemProbe` only if the hard-block path was taken (which terminates the app anyway).
- **Memory tools registration.** Live BootHealth: `10 tools (3 stdio + 7 in-process)` including `search_memory`, `forget_fact`, `get_memory_stats`. The tools are registered and dispatch-routable — only the discoverability cue is missing (M-3).
- **Single-emit grep gates.** `scripts/check-single-memory-mutated-emit.sh` and `scripts/check-single-memory-used-emit.sh` both pass at HEAD. MemoryStore is the sole construction site for both `ReplayEvent.memoryMutation` and `ReplayEvent.memoryRetrieval`.

## Open questions

- **Was M-1 (no facts_vec writes) ever intended to ship?** The schema comment + `SearchMemoryTool.toolDescription` ("semantic (vec0)") strongly suggest yes. The orchestrator's `process(_:)` would be the natural place to call the embedder after `applyOp` returns the new fact. Likely a Phase-7 deferral that never landed — analogous to D-5/D-6 except no corresponding TODO line tracks it. Worth checking whether anyone noticed the gap during the 2026-05-04 audit (synthesis report mentions vec0 as a deferred environment problem, but doesn't mention the writer-side gap).
- **Should `MemoryExtractor` ALSO call the embedder for `priorActiveFacts` rendering?** Probably not — the priorFacts go into the system prompt as text; vec only matters when searching. Out of scope unless M-1 fix surfaces it.
- **Is the `OrchestratorEvent.memoryMutated` referenced in the audit prompt's scope §6 a planned event?** I couldn't find it in any current source. If it's planned for v1.0 migration, M-1/M-2 should be addressed before the bus forwarding lands — otherwise the HUD card will be wired to a dead pipeline.
- **M-2 mitigation choice.** The synthetic-turn-id approach is a Phase-7 design (the trigger turn for memory mutation is real, but the mutation can in principle span multiple turns). Real-turn-id threading is cleaner but adds API surface. Sentinel turn rows are the smallest fix. User preference?
- **Does `MemoryExtractor` ever actually fire today?** Replay events show 19 `tool_call_requested` rows but extractor calls aren't on the same code path (extractor uses local Ollama, not the agent loop's replay log). Live `memory.2026-05-12.log` doesn't show extractor-issued log lines (the extractor only logs the failure modes — "no apply_memory_ops tool call"). If the extractor is firing but the qwen3.6:latest model isn't returning the tool call, we have no signal. **Recommended:** add INFO logging to `MemoryExtractor.extract` on the success path so the orchestrator's drain progress is observable. Today's "1 fact persisted" implies it fired at least once, but the orchestrator log only shows the pre-fix failures.
