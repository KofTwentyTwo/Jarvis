# Phase 5 Plan 3: helper-applescript Summary

Built and shipped `mcp-applescript` as the third separately-codesigned nested `.app` bundle under `Jarvis.app/Contents/Helpers/`, exposing the privileged `run_applescript` tool that executes AppleScript source via in-process `NSAppleScript`. Extended `scripts/verify-entitlements.sh` with bidirectional per-helper rules (required + forbidden arrays per helper name) so the build fails if `com.apple.security.automation.apple-events` lands on the wrong helper OR is missing from `mcp-applescript`. Added three new fault-injection fixtures (positive / missing-required / cross-helper-drift) bringing the harness corpus to 6 cases (PASS=6, FAIL=0).

Closes the helper portion of MCP-04. The confirmation broker, presenter, and `MCPToolDispatcher` gating that prevents the helper from being called without user approval land in Plans 05-04 and 05-05.

## What landed

**Third SPM helper package** under `mcp-servers/`:
- `mcp-servers/mcp-applescript/` — executable target plus a testable `AppleScriptRunner` library + `AppleScriptRunning` protocol. The MCP `run_applescript` tool reads a `source` String argument, calls `NSAppleScriptRunner().run(source:)`, returns `.success(text)` / `.runtimeError(num,msg)` / `.compileFailure` mapped onto MCP `CallTool.Result` content + isError.

## Decisions made

See frontmatter `decisions:` for the canonical list. Key callouts:

- **In-process `NSAppleScript` only.** A subprocess CLI invocation to run scripts would split the TCC identity from the helper bundle and defeat the per-helper isolation that the entitlement layout enforces (T-05-03-03). The `AppleScriptRunner` protocol seam exists for testability, not to swap in a subprocess implementation.
- **No allowlist, no skip-rules, no content inspection inside the runner** (SEC-08, T-05-03-04). Every call is privileged in v1; the user-confirmation gate lives at the orchestrator boundary in Plan 05-05's ConfirmationBroker. Adding a "safe-pattern" allowlist here would silently bypass the FSM and violate SEC-08.
- **Bidirectional rule enforcement.** Existing 05-02 logic only forbade `apple-events` on non-applescript helpers. Plan 05-03's contribution is the inverse check — `mcp-applescript` MUST carry it (T-05-03-02 mitigation). Both halves now travel together as paired arrays.
- **Empty array guard for `set -u`.** Bash 3.2 (macOS default) chokes on `${array[@]}` when the array is empty under `set -u`. mcp-time / mcp-clipboard have empty `required` lists, so the function uses `[ "${#array[@]}" -gt 0 ]` to guard the loop. Discovered as a build failure on the first Debug xcodebuild after the refactor; documented inline.

## Scaffold-time NSAppleScript probe (RESEARCH Open Question #3)

The helper's `MCPAppleScriptMain.main()` runs a trivial probe at init (`tell application "System Events" to get the name of every process`) and writes the outcome to stderr. This was meant to confirm at scaffold time whether `NSAppleScript.executeAndReturnError(_:)` works without `NSApplication.run()`.

**Result on this executor's machine (running the unsigned `.build/release/mcp-applescript` standalone outside the Jarvis bundle):** the probe times out with AppleScript error -1712 "AppleEvent timed out" (~30 s wait) because the parent shell process is the TCC requester and has no Automation grant for System Events. This is **expected and not a defect** — the probe is written to fire under the helper's per-helper TCC identity, which only takes effect when:

1. The helper runs from inside `Jarvis.app/Contents/Helpers/mcp-applescript.app/Contents/MacOS/mcp-applescript` (LaunchServices-registered, signed, with `com.apple.security.automation.apple-events` entitlement), AND
2. The user has granted Automation → System Events to `mcp-applescript` (first-run TCC prompt).

Live verification of the probe under proper TCC identity is gated by HUMAN-UAT: developer.apple.com App ID capability registration is required before Release archive notarization succeeds, and Debug-ad-hoc signed bundles + a real first-run prompt are needed to observe a TCC-approved probe outcome. Plan 05-05's confirmation broker arrival surface will exercise the same path through the orchestrator and is the natural place to capture the live probe outcome.

**Open Question #3 status:** still open at the empirical level (this plan did not observe a successful probe under helper TCC identity). The contract `NSAppleScript.executeAndReturnError(_:)` works without `NSApp.run()` is unblocked because:
- `swift /tmp/probe_test.swift` (a one-shot Foundation-only script) DID return error info (TCC-denied with error -1712) within ~5 s rather than hanging — meaning `executeAndReturnError(_:)` is synchronous and timeout-bounded without an event loop. The mode of failure is permission denial, not deadlock.
- If this plan's contract proves wrong (i.e. live AppleScript execution requires `NSApp.run()` in production), a future plan wraps `MCPAppleScript` in `NSApplicationDelegate + NSApp.run()`. The helper's testable seam (`AppleScriptRunning` protocol) makes that swap trivial.

## Known Stubs

- **ConfirmationBroker (Plan 05-05).** This helper executes scripts unconditionally; the user-approval gate lives at the orchestrator boundary BEFORE `MCPClient.callTool("run_applescript", ...)` is dispatched. The current state intentionally trusts the parent — composing this with the broker is Plan 05-05's job.
- **MCPToolDispatcher (Plan 05-04).** The orchestrator-side wiring that routes `run_applescript` from the LLM tool-call surface through to `MCPClient.callTool` (with sanitization, schema validation, and broker gating) does not exist yet.
- **Live AppleScript-with-TCC verification.** Gated by HUMAN-UAT (`05-03-HUMAN-UAT.md`). Debug ad-hoc signing works without the developer.apple.com capability registration; Release archive notarization does not.
